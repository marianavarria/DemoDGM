## 1. Objective of this report

The objective was **not** to numerically replicate the paper's results on Polyglot, paper review, robotics, and IMO-GradingBench, because each of those benchmarks requires Docker, Linux, heavy dependencies (Genesis, Balrog), and calls to large Foundation Models with paid APIs. Instead, the objective was to **reproduce on a small scale, on Windows, the same algorithmic concepts**:

- open-ended archive of agents;
- meta-agent capable of modifying itself (metacognitive self-modification);
- probabilistic parent selection;
- empirical evaluation of the child before insertion into the archive;
- iterative cycle `generate → evaluate → archive → select → modify`.

## 2. Theoretical context

### 2.1 From Gödel Machine to DGM

The idea of a self-improving AI dates back to Schmidhuber's theoretical work on the **Gödel Machine** (2003). In those models, a modification is applied only if the agent can formally prove that it is beneficial. This constraint makes them impractical in the real world.

With Foundation Models, a different approach became possible: instead of **proving** that a modification is beneficial, it is **evaluated empirically** on a benchmark. This idea underlies the **Darwin Gödel Machine** (DGM, Zhang et al. 2025, arXiv 2505.22954), which starts from a coding agent and evolves it in an open-ended way.

In the DGM:

- the agent is a Python program that uses `bash` and `editor` tools;
- at each iteration, a fixed hand-written mechanism (`diagnose_prompt`) analyzes the logs and proposes an improvement direction;
- a new agent is generated by modifying the parent's code;
- the child is evaluated on SWE-bench or Polyglot and, if it compiles, enters an archive.

The limitation of the DGM is that the **improvement mechanism is fixed**: it only works for coding tasks, because the same coding ability is used both to solve the task and to modify the agent's code. If the task is not coding (e.g. peer review of papers), the alignment assumption breaks down.

### 2.2 The DGM-Hyperagents shift

DGM-Hyperagents (DGM-H), published the following year by the same authors, removes this limitation. The key definition in the paper is:

> *A hyperagent is a self-referential agent that integrates a task agent and a meta agent within a single editable program, enabling it to modify not only how it performs tasks but also how it generates future self-modifications.*

In practice:

- **Task agent**: the agent that solves the task (paper review, reward design, palindromes in our case).
- **Meta agent**: the agent that modifies other agents, decides what to change in the code.
- **Hyperagent**: a single editable program that contains **both**, and therefore can modify both the task agent and itself (the meta agent).

This property is called **metacognitive self-modification**. It means that the system improves not only how it solves the task, but also how it generates future modifications.

Important consequence: DGM-H no longer assumes that task and self-improvement coincide. It therefore works on very different domains. In the paper the authors demonstrate it on four domains:

- **Coding** (Polyglot benchmark): 60 training tasks, 165 test tasks.
- **Paper review**: binary accept/reject classification on 100 papers.
- **Robotics reward design** (Genesis, Go2 robot): generation of reward functions for robotic control via PPO.
- **Olympiad-level math grading** (IMO-GradingBench): evaluation of solutions to IMO problems.

### 2.3 The algorithmic cycle (Algorithm 1 of the paper)

```text
Input: initial agent a^0, task set T, iterations T_max
Output: archive A

1. A = { (a^0, evaluate(a^0, T)) }
2. for t = 1 .. T_max:
3.     P = SelectParents(A)
4.     for (a, _) in P:
5.         a' = a.Modify(a, A)
6.         s' = Evaluate(a', T)
7.         if IsValid(a'):
8.             A = A ∪ { (a', s') }
9. return A
```

Three ingredients make the cycle "open-ended":

- **growing archive**: every valid agent remains as a *stepping stone* for the future;
- **probabilistic parent selection**: balances exploitation (who performs best) and exploration (who is under-explored);
- **code-level self-modification**: the child is obtained by modifying the parent's code.

In DGM-H the entire program is editable, so even `Modify` and `SelectParents` can be rewritten. This is the conceptual difference from the original DGM.

### 2.4 The three baselines of the paper

To measure which component of DGM-H is truly important, the authors compare DGM-H with three ablated baselines (Sec. 4.1):

| Method | Self-improving meta | Open-ended exploration | Hyperagent |
|---|:-:|:-:|:-:|
| **DGM-H** | yes | yes | yes |
| `DGM-H w/o self-improve` (≈ ADAS) | no | yes | yes |
| `DGM-H w/o open-ended exploration` | yes | no | yes |
| Original **DGM** | yes | yes | no (fixed mechanism) |

**Demo 1 and Demo 2** reproduce exactly the two ablations of these central rows.

### 2.5 DGM-H parent selection (Sec. 8.2)

At each iteration, the authors compute a weight for each agent in the archive:

1. **Dynamic midpoint**: mean of the top-3 agent scores, `α_mid = mean(top3(α_i))`.
2. **Sigmoid**: `s_i = 1 / (1 + exp(-λ · (α_i - α_mid)))` with `λ = 10`.
3. **Novelty bonus**: `h_i = 1 / (1 + n_i)` with `n_i` = number of compiled children.
4. **Final weight**: `w_i = s_i · h_i`, normalized into probabilities.

The weight is high for agents that **are above the current performance frontier** and that **have generated few children**. **Demo 3** implements these formulas faithfully.

### 4.2 `CandidateProgram`

A `CandidateProgram` is the code of a task agent **as a Python string**. The `compile()` function executes it with `exec()` and returns the `solve(x)` function. This reproduces the fact that, in the real DGM, each agent is modifiable code.

```python
@dataclass(frozen=True)
class CandidateProgram:
    name: str
    description: str
    code: str

    def compile(self) -> Callable[[Any], Any]:
        namespace: dict[str, Any] = {}
        exec(self.code, {}, namespace)
        solve = namespace.get("solve")
        if not callable(solve):
            raise ValueError("The program does not define solve(x).")
        return solve
```

**Why strings and not Python functions?**  
Because we want to simulate the fact that the meta-agent **modifies textual code**, not live objects in memory. In the real DGM the meta-agent invokes the `editor` tool to rewrite `.py` files; here mutations are new strings.

### 4.3 `TaskAgent`

Just a wrapper around `CandidateProgram`: takes an input and returns the prediction of `solve(input)`.

```python
@dataclass
class TaskAgent:
    program: CandidateProgram

    def solve(self, item: Any) -> Any:
        return self.program.compile()(item)
```

### 4.4 `MetaAgent`

This is the heart of the simulation, because it encapsulates the **ability to propose modifications**. In the paper, this is the quintessential editable part. Here it is deterministic, but simulates two key behaviors from the paper:

1. **Progressive expansion of the mutation repertoire**: `hidden_candidates` are unlocked only when the archive reaches `unlock_score_threshold`. This replicates the idea that a meta-agent improves over time: it does not always generate the same modifications, but "discovers" more sophisticated strategies as it observes better results in the archive.
2. **Persistent memory** (`mutation_memory`): records unlock events. Simulates the *persistent memory* described in Sec. 5.2 of the paper, where the authors show that DGM-H autonomously develops structures to track improvements over time.

```python
@dataclass
class MetaAgent:
    base_candidates: list[CandidateProgram]
    hidden_candidates: list[CandidateProgram] = field(default_factory=list)
    self_improve: bool = True
    unlock_score_threshold: float = 0.75
    mutation_memory: list[str] = field(default_factory=list)
    unlocked: int = 0

    def generate_candidates(self, parent, archive):
        best_score = max((e.train_score for e in archive), default=0.0)
        if self.self_improve and self.unlocked < len(self.hidden_candidates):
            if best_score >= self.unlock_score_threshold:
                candidate = self.hidden_candidates[self.unlocked]
                self.unlocked += 1
                self.mutation_memory.append(
                    f"Unlocked meta strategy: {candidate.name}"
                )
        return self.base_candidates + self.hidden_candidates[: self.unlocked]
```

**Case `self_improve=True`**: the meta-agent improves its own mutation repertoire. Replicates the full `DGM-H`.  
**Case `self_improve=False`**: the meta-agent remains frozen at the initial state. Replicates the `DGM-H w/o self-improve` baseline, equivalent to ADAS (Hu et al. 2024).

### 4.5 `HyperAgent`

Combines task agent and meta-agent in the same object. When a hyperagent self-modifies, it **inherits a copy (clone) of the parent's meta-agent**. Thus meta-cognitive discoveries (the state of `unlocked` and `mutation_memory`) propagate along the genealogy.

```python
@dataclass
class HyperAgent:
    task_agent: TaskAgent
    meta_agent: MetaAgent
    generation: int = 0

    def modify(self, archive, rng, candidates_per_iteration: int = 1):
        candidates = self.meta_agent.generate_candidates(self, archive)
        selected = rng.sample(candidates, k=min(candidates_per_iteration, len(candidates)))
        return [
            HyperAgent(
                task_agent=TaskAgent(c),
                meta_agent=self.meta_agent.clone(),
                generation=self.generation + 1,
            )
            for c in selected
        ]
```

### 4.6 `ArchiveEntry`

One row of the archive. Tracks everything needed for analysis, plots, and genealogy reconstruction:

- `node_id`, `parent_id`: to reconstruct the agent tree;
- `iteration`: for temporal plots;
- `train_score`, `test_score`: dual evaluation to measure generalization;
- `valid`: `False` if the code does not compile or raises an exception;
- `seed`, `variant`: to distinguish multiple runs and configurations.

### 4.7 The 4 parent selection strategies

Faithfully reproduce what is described in Sec. 8.2 of the paper. All are functions `(archive, rng) → ArchiveEntry`:

```python
def select_random(archive, rng):
    return rng.choice(archive)

def select_best(archive, rng):
    best_score = max(e.train_score for e in archive)
    best_entries = [e for e in archive if e.train_score == best_score]
    return rng.choice(best_entries)

def _score_weights(archive):
    top_scores = sorted((e.train_score for e in archive), reverse=True)[:3]
    midpoint = mean(top_scores)
    return [1 / (1 + math.exp(-10 * (e.train_score - midpoint))) for e in archive]

def select_score_prop(archive, rng):
    return rng.choices(archive, weights=_score_weights(archive), k=1)[0]

def select_score_child_prop(archive, rng):
    counts = child_counts(archive)
    weights = [
        w * (1 / (1 + counts[e.node_id]))
        for e, w in zip(archive, _score_weights(archive))
    ]
    return rng.choices(archive, weights=weights, k=1)[0]
```

- `random`: pure exploration. Baseline.
- `best`: pure exploitation. Opposite baseline.
- `score_prop`: probability proportional to the sigmoid of `(α − α_mid)`. **Identical formula to Sec. 8.2 of the paper**.
- `score_child_prop`: as above, multiplied by novelty bonus `1/(1+n_children)`. **Default strategy of the official DGM-H**.

## 5. Execution flow

### 5.1 The `run_dgm_h` cycle

Everything goes through a single function `run_dgm_h` in `common.py`, which reproduces Algorithm 1 of the paper:

```python
def run_dgm_h(*, variant, train_data, test_data, initial_program, meta_agent,
              selector=select_score_child_prop, iterations=30, seed=0,
              archive_mode="full", candidates_per_iteration=1):
    rng = random.Random(seed)
    initial_agent = HyperAgent(TaskAgent(initial_program), meta_agent, generation=0)
    archive = [ArchiveEntry(node_id=0, parent_id=None, iteration=0,
                            agent=initial_agent,
                            train_score=evaluate(initial_agent, train_data),
                            test_score=evaluate(initial_agent, test_data),
                            valid=is_valid(initial_agent),
                            seed=seed, variant=variant)]
    history = list(archive)
    next_id = 1
    for iteration in range(1, iterations + 1):
        parent = selector(archive, rng)
        children = parent.agent.modify(archive, rng,
                                       candidates_per_iteration=candidates_per_iteration)
        new_entries = []
        for child in children:
            valid = is_valid(child)
            entry = ArchiveEntry(
                node_id=next_id, parent_id=parent.node_id, iteration=iteration,
                agent=child,
                train_score=evaluate(child, train_data) if valid else 0.0,
                test_score=evaluate(child, test_data) if valid else 0.0,
                valid=valid, seed=seed, variant=variant)
            next_id += 1
            new_entries.append(entry)
            history.append(entry)
        if archive_mode == "last_only":
            archive = new_entries or archive[-1:]
        elif archive_mode == "full":
            archive.extend(new_entries)
    return history
```

### 5.3 Difference between `archive` and `history`

There is an important subtlety: the function maintains **two structures**:

- `archive`: the one from which the parent is selected. In `last_only` mode it is reset at each iteration.
- `history`: the complete history, **always** maintained. Used to generate CSV and plots.

This way, even the `senza_archivio` baseline produces comparable data (we see what it could have done, even though it is not actually using it for selection).

## 6. Demo 1 — Archive ablation

### 6.1 Purpose

Measure the effect of the open-ended archive on the DGM-H cycle. We want to understand whether keeping all stepping stones helps compared to keeping only the last generated agent.

### 6.2 Mapping to the paper

Replicates the `DGM-H w/o open-ended exploration` baseline (Algorithm 3, Sec. 9). In the paper, removing the archive causes performance to collapse on paper review (test score 0.0) and robotics reward design (test score 0.116).

configs = {

| Variant | Final mean | Min | Max | Std | Mean convergence iteration |

| `con_archivio` | **1.000** | 1.000 | 1.000 | 0.000 | **6.4** |

### 6.6 Graph explanation (`ablation_archive.png`)

The graph shows two curves, one per variant, of the mean best test score over the 5 seeds as a function of iteration (0..30). Both start at 0.5 (the naive initial agent) and rise rapidly, reaching 1.0 around iteration 6-7. The two curves are almost overlapping.

### 6.7 Interpretation

On our didactic task the correct mutation is reachable in 1-2 steps, so the archive does not make much difference: even keeping only the last agent, sooner or later the meta-agent proposes the right strategy.

- This demo is a **structural ablation**: it shows what it means in code to "remove open-ended exploration", but on such small tasks the gain is not visible. In the paper's real experiments (Figure 2) the difference is enormous: the same baseline collapses to zero on paper review.

## 7. Demo 2 — Self-improve ablation

### 7.1 Purpose

Measure the effect of **metacognitive self-modification**, i.e. the meta-agent's ability to improve over time. This is the **central** idea of the paper.

### 7.2 Mapping to the paper

Replicates the comparison between `DGM-H` (full) and `DGM-H w/o self-improve` (Sec. 5.1, Figure 2 of the paper). In the paper, on paper review the baseline without self-improve stops at 0.0, while DGM-H reaches 0.710. On robotics the difference is 0.213 vs 0.372.

### 7.3 Experimental setup

| Parameter | Value |
|---|---|
| Task | Palindrome classification (reduced version) |
| Train | 8 examples |
| Test | 6 examples |
| Iterations | 30 |
| Seed | 5 (0..4) |
| Selector | `score_child_prop` |
| Archive mode | `full` |

**Base mutations**: `always_true`, `always_false`, `first_last_equal` (partial heuristic: first and last character only).  
**Hidden mutation**: `reverse_check` (correct, but unlockable only if `self_improve=True`).

### 7.4 Relevant code

```python
for variant, self_improve in {
    "meta_congelato": False,
    "meta_self_improve": True,
}.items():
    for seed in SEEDS:
        archive = run_dgm_h(
            variant=variant,
            train_data=TRAIN_DATA,
            test_data=TEST_DATA,
            initial_program=make_initial(),
            meta_agent=make_meta(self_improve),
            selector=select_score_child_prop,
            iterations=ITERATIONS,
            seed=seed,
            archive_mode="full",
        )
        rows.extend(best_by_iteration(archive))
```

### 7.5 Results

| Variant | Final mean | Min | Max | Std | Mean convergence iteration |
|---|---:|---:|---:|---:|---:|
| `meta_congelato` | **0.667** | 0.667 | 0.667 | 0.000 | never converges |
| `meta_self_improve` | **1.000** | 1.000 | 1.000 | 0.000 | **10.6** |

### 7.6 Graph explanation (`ablation_self_improve.png`)

This is the key graph of the report. Two clear curves:

- `meta_congelato` (lower line): grows rapidly from 0.5 to 0.667 in the first 2-3 iterations, then **flat at 0.667 for all 30 iterations**. The best available strategy is `first_last_equal`, which is correct only for some test cases.
- `meta_self_improve` (upper line): follows the same path up to 0.667, but then at some point the meta-agent unlocks `reverse_check` and the curve rises to 1.0. Convergence occurs on average at iteration **10.6**.

### 7.7 Interpretation

This is the most important result of the report. The difference **0.667 vs 1.000** is statistically significant in our setup and is **the only one** of our demos to show a true quantitative difference between variants.

It concretely demonstrates the HyperAgents thesis: **improving only the task agent is not enough**. If the modification generation mechanism is fixed, the system is blocked by its initial repertoire. Only if the meta-agent can expand its own repertoire (here simulated by progressive unlocking, in the paper realized by an LLM that rewrites the meta-agent code) is the performance ceiling broken.

## 8. Demo 3 — Parent selection strategies

### 8.1 Purpose

Compare the four parent selection strategies from the archive. We want to understand how exploration and exploitation balance each other.

### 8.2 Mapping to the paper

**Faithfully** implements the formulas from Sec. 8.2 of the paper: dynamic midpoint on top-3 scores, sigmoid with `λ = 10`, novelty bonus `1/(1+n_children)`.

### 8.3 Experimental setup

| Parameter | Value |
|---|---|
| Task | Palindrome classification |

| Test | 8 examples |

### 8.4 Relevant code

```python
PARENT_SELECTORS: dict[str, Callable[..., ArchiveEntry]] = {
    "random": select_random,
    "best": select_best,
    "score_prop": select_score_prop,
    "score_child_prop": select_score_child_prop,
}

    for seed in SEEDS:

            variant=selector_name,
            train_data=TRAIN_DATA, test_data=TEST_DATA,

            seed=seed, archive_mode="full",
        )

```

### 8.6 Graph explanation (`parent_selection.png`)

### 9.4 Relevant code

```python
def make_meta() -> MetaAgent:
    base = [
        CandidateProgram("always_true", "...", "def solve(x):\n    return True\n"),
        CandidateProgram("always_false", "...", "def solve(x):\n    return False\n"),
        CandidateProgram("contains_vowel", "...",
            "def solve(x):\n    return any(ch in 'aeiou' for ch in x.lower())\n"),
        CandidateProgram("starts_with_vowel", "...",
            "def solve(x):\n    return bool(x) and x[0].lower() in 'aeiou'\n"),
    ]
    hidden = [
        CandidateProgram("only_vowels", "Checks that all characters are vowels.",
            "def solve(x):\n    vowels = set('aeiou')\n    "
            "return bool(x) and all(ch in vowels for ch in x.lower())\n")
    ]
    return MetaAgent(base_candidates=base, hidden_candidates=hidden,
                     self_improve=True, unlock_score_threshold=0.70)
```

### 9.7 Interpretation

## 10. Demo 5 — Mini code-repair

### 10.1 Purpose

Move closer to the original DGM domain: repair of faulty code evaluated by tests. Replicates in miniature the Polyglot/SWE-bench scenario.

### 10.2 Mapping to the paper

DGM-H inherits the DGM design, which was born precisely for coding. Sec. 5.1 of the paper reports that DGM-H reaches **0.267** on the Polyglot benchmark, comparable to the original DGM (0.307). Our demo is an ultra-simplified version of that scenario.

### 10.3 Experimental setup

| Parameter | Value |
|---|---|
| Initial function | `def solve(x): a, b = x; return a - b` (bug: subtraction) |
| Train | 5 input-output |
| Test | 4 input-output |
| Iterations | 25 |
| Seed | 5 |
| Unlock threshold | 0.20 (lowered) |

**Candidate patches**: `return a`, `return b`, `a * b`, `abs(a - b)`.  
**Correct hidden patch**: `a + b`.

Low threshold: the buggy function (`a - b`) already has positive score on some cases (e.g. `add(5, 7)` produces `-2` ≠ 12, but `add(-1, 4)` produces `-5` ≠ 3, etc.), and we lower it to allow unlocking of `a + b`.

### 10.4 Relevant code

```python
TRAIN_DATA = [
    ((1, 2), 3), ((0, 0), 0), ((5, 7), 12), ((-1, 4), 3), ((10, -3), 7),
]
TEST_DATA = [
    ((2, 3), 5), ((-2, -8), -10), ((100, 1), 101), ((8, -8), 0),
]

def make_initial():
    return CandidateProgram(
        "buggy_subtraction",
        "Initial bug: uses subtraction instead of addition.",
        "def solve(x):\n    a, b = x\n    return a - b\n",
    )
```

### 10.5 Results

| Variant | Final mean | Std | Mean convergence iteration |
|---|---:|---:|---:|
| `mini_code_repair` | 1.000 | 0.000 | **4.8** |

Converges faster than the other demos (4.8 iterations) because the patch space is small and the correct patch is well defined.

### 10.6 Graph explanation (`code_repair.png`)

A single curve: starts at 0 (the original `a-b` bug solves none of the tests), rises to about 0.2 with `abs(a-b)` which sometimes coincides with `a+b`, and finally reaches 1.0 when the meta-agent unlocks `a + b`.

### 10.7 Interpretation

This is the demo closest to the **original DGM**. The cycle is clearly visible:

1. initial bug → low score;
2. the meta-agent proposes candidate patches;
3. each is evaluated on the tests;
4. the best enters the archive;
5. after a few iterations the correct patch is unlocked.

It is also the demo most naturally extensible to a **real LLM** as meta-agent: it would suffice to replace the predefined list with a call to a model that produces real patches.

## 14. Discussion and interpretation

### 14.1 What works

- The cycle `generate → evaluate → archive → select → modify` works on all three types of tasks tried (palindrome classification, vowel classification, code-repair).
- The archive grows in an open-ended way and produces a traceable genealogy (`parent_id`).
- The four parent selection strategies are implemented faithfully to the formulas of Sec. 8.2 of the paper.
- The difference between frozen meta-agent and evolving meta-agent is clear and replicates the paper's central thesis.

### 14.2 What converges too easily

On such small tasks (8-12 training examples, 6-10 test):

- The archive ablation shows no differences because the correct mutation is reachable in a few steps without needing intermediate stepping stones.
- All four parent selection strategies converge: only a modest speed difference is visible.

This is not an implementation problem, but an **inherent** limitation of the didactic scale. In the paper, benchmarks have 60-200 tasks and 80-100 iterations, and those differences become enormous.

### 14.3 The key result (Demo 2)

The difference **0.667 vs 1.000** is the conceptual reproduction of what the authors demonstrate at enormous scale:

| Paper domain | DGM-H | DGM-H w/o self-improve | Gap |
|---|---:|---:|---:|
| Paper review (test) | 0.710 | 0.0 | 0.710 |
| Robotics reward (test) | 0.372 | 0.213 | 0.159 |
| **Our Demo 2** | **1.000** | **0.667** | **0.333** |

Our setup is enormously smaller and with the LLM replaced by a mutation list, but the qualitative pattern is the same: **removing the meta-agent's self-improvement capability significantly worsens final performance**.

### 14.4 Why all this matters

The underlying message of the paper, which our mini-replica supports, is:

> *To build AI truly capable of self-improvement on any computable task, it is not enough to improve the task agent. One must design systems in which even the mechanism that generates improvements can be modified by the system itself.*

Without this, every self-improvement system remains blocked by its initial design.
